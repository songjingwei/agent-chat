# Agent Chat MVP 实施计划（Priority-first + 低成本）

## 1. 目标与约束

### 1.1 MVP 目标
在 15 个工作日内交付可演示版本，并优先验证这 4 个核心价值：
1. `像本人`：persona 能反映用户特征。
2. `能自主`：双 agent 可持续多轮对话。
3. `可控`：用户介入后可显著改变后续行为。
4. `有用`：会话后可输出可解释总结和推荐。

### 1.2 预算约束
1. MVP 阶段按“零预算优先”设计。
2. 先本地自托管，后再考虑免费层云服务。
3. 任何新增服务都必须先回答：不花钱能否替代。

### 1.3 当前进度快照（As of 2026-03-22）
1. Day 0 已完成且超额交付：monorepo 骨架、`.env.example`、API 初始化、Web 初始化、模块说明文档。
2. Day 1 已提前完成：`docs/core-metrics.md` 已定义 3 个核心指标；`Docker 20.10.21` 与 `Docker Compose v2.13.0` 已验证可用。
3. Day 2 进行中：`infra/docker/docker-compose.yml` 与 `GET /health` 已落地，但依赖拉起、DB/Redis 探针和基础 trace 日志仍待补齐。
4. 当前未完成：核心数据表与迁移、Runtime、Worker、持久化、实时推送、正式鉴权。

## 2. 优先级定义（最重要任务先完成）

### P0（必须在前 7 天完成）
1. Agent Runtime 状态机（可控、可追踪）。
2. 记忆层设计与权重策略（尤其 Human Override）。
3. 双 agent 对话闭环（含持久化）。
4. 用户介入后重塑行为闭环。
5. 基础评估体系（不是靠主观感觉）。

### P1（P0 稳定后完成）
1. 总结与推荐 v1。
2. 安全与脱敏基础链路。
3. 最小可演示 UI（会话回放 + 实时消息）。

### P2（最后做）
1. 正式注册登录。
2. 高级推荐排序。
3. 运营后台和实验平台。

## 3. 低成本技术栈与服务建议

### 3.1 零预算优先（推荐先用这个）
1. Monorepo：`pnpm workspace`。
2. 前端：`TanStack Start`（本地运行）。
3. API：`Hono.js`（本地运行）。
4. DB：本地 `PostgreSQL + pgvector`（Docker）。
5. 队列与缓存：本地 `Redis`（Docker）。
6. 对象存储：本地 `MinIO`（Docker）。
7. AI：开发阶段先用 `Mock/回放`，仅关键评估再调真实模型。

### 3.2 需要线上 Demo 时（尽量免费层）
1. 前端/API 边缘层：Cloudflare（免费层可先用）。
2. Postgres：Neon 或 Supabase 免费层二选一。
3. Redis：Upstash 免费层。
4. 对象存储：Cloudflare R2 免费层起步。
5. CI：GitHub Actions 免费额度内运行。

说明：
1. 免费层策略和额度会变，落地前要再次核对官方 pricing 页面。
2. 如果免费层不稳定，优先回退到本地演示方案，不要提前付费。

### 3.3 AI 成本控制（强制）
1. 所有请求设置 `max_tokens` 和超时。
2. 对话上下文做摘要压缩，不拼接超长历史。
3. 结果缓存（相同 persona + 相似上下文命中缓存）。
4. 把总结、分类等任务放到更低成本模型。
5. 每日设置 token/cost 上限，超限自动降级到 mock。

## 4. Day-by-Day 计划（按优先级排序）

### Day 1：定义成功标准 + 工程底座
目标：先把“成败标准”定清楚，再开工。
步骤：
1. 定义 3 个核心指标：`persona_fidelity`、`controllability`、`summary_usefulness`。
2. 初始化 `pnpm workspace` 与 monorepo 目录结构。
3. 建立 `.env.example`、日志字段、错误码规范。
交付物：
1. 工程可启动，指标定义文档可审阅。
验收标准：
1. 团队对 MVP 成功标准达成一致。

### Day 2：本地基础设施（零预算模式）
目标：不花钱跑起全部依赖。
步骤：
1. 编写 `docker-compose`（PostgreSQL、Redis、MinIO）。
2. API 健康检查（DB/Redis 连通）。
3. 建立基础 trace 日志。
交付物：
1. 本地一键启动脚本。
验收标准：
1. 全部依赖启动稳定，可重复。

### Day 3：Agent 核心数据模型
目标：先把最关键数据结构定死。
步骤：
1. 建表：`agent_personas`、`memory_items`、`chat_sessions`、`chat_messages`、`match_reports`、`profiles`。
2. 明确记忆权重字段和来源字段。
3. 建立种子数据与最小测试用户机制。
交付物：
1. 数据迁移脚本与种子脚本。
验收标准：
1. 可创建会话并写入消息与记忆。

### Day 4：Agent Runtime v1（P0）
目标：实现受控、可追踪的 agent 执行核心。
步骤：
1. 实现状态机骨架和工具调用接口。
2. 强制结构化输出（JSON schema）。
3. 增加失败重试和兜底回复。
交付物：
1. 单 agent 在固定输入下稳定输出。
验收标准：
1. 核心链路可重复执行。

### Day 5：Persona Builder（P0）
目标：从资料生成 persona，并支持可回滚版本。
步骤：
1. 资料 -> persona 的结构化生成流程。
2. persona 版本化存储。
3. 人工编辑接口与变更审计。
交付物：
1. persona 生成/编辑 API。
验收标准：
1. 单用户可管理多个 persona 版本。

### Day 6：双 Agent 自动对话（P0）
目标：跑通双 agent 多轮自动对话。
步骤：
1. Worker 实现 A/B 轮询对话。
2. 每轮读取记忆并持久化消息。
3. 设置最大轮次和超时保护。
交付物：
1. 创建会话后自动产出多轮消息。
验收标准：
1. 对话可稳定结束，不死循环。

### Day 7：用户介入高权重重塑（P0 完成日）
目标：验证“可控性”核心价值。
步骤：
1. 增加 `human_message` 接口。
2. 用户输入写入高权重记忆层。
3. 下一轮强制读取并生效。
交付物：
1. 人工介入可影响后续对话。
验收标准：
1. 介入后至少连续 2 轮可观察行为变化。

### Day 8：评估体系落地（P0 验证）
目标：把“主观感觉”变成“可对比数据”。
步骤：
1. 准备 20-50 条离线场景测试集。
2. 编写自动评测脚本。
3. 输出基线分数和回归报告格式。
交付物：
1. `eval` 工具和基线结果。
验收标准：
1. 每次改动可自动比较前后质量。

### Day 9：总结与推荐 v1（P1）
目标：补齐“有用性”输出。
步骤：
1. 定时汇总会话。
2. 生成推荐对象与解释理由。
3. 落表并提供查询 API。
交付物：
1. `GET /reports/latest` 可用。
验收标准：
1. 每条推荐都带可读依据。

### Day 10：安全与隐私基础（P1）
目标：避免明显风险上线。
步骤：
1. 输入/输出敏感内容检查。
2. 上传文本脱敏预处理。
3. 审计日志写入关键操作。
交付物：
1. 安全中间件和审计查询。
验收标准：
1. 核心链路全部经过安全检查。

### Day 11：最小可演示 UI（P1）
目标：能完整演示核心链路。
步骤：
1. 会话列表与详情页。
2. 实时消息推送与历史回放。
3. 介入输入与总结查看。
交付物：
1. 从发起会话到看总结的 UI 闭环。
验收标准：
1. Demo 用户可独立走完流程。

### Day 12：广场与匹配入口（P1）
目标：完善“找对象 -> 开聊”入口。
步骤：
1. 广场列表接口和基础排序规则。
2. 发起会话入口与状态提示。
3. 失败重试和空状态处理。
交付物：
1. 广场可用。
验收标准：
1. 用户可从广场发起并进入会话。

### Day 13：最小身份隔离（P2 前置）
目标：先保证数据隔离，不做重账户体系。
步骤：
1. 临时身份机制（device token 或 magic link）。
2. user scope 数据隔离中间件。
3. 权限边界测试。
交付物：
1. 不同用户数据可隔离。
验收标准：
1. 用户 A 无法访问用户 B 数据。

### Day 14：正式登录注册（P2，可选）
目标：仅在前面稳定后再补。
步骤：
1. 注册/登录/JWT 刷新。
2. 兼容临时身份迁移。
3. 限流与安全策略。
交付物：
1. 标准账户 API。
验收标准：
1. 登录后历史数据关联正确。

### Day 15：联调、成本压测与发布
目标：形成可持续演示版本。
步骤：
1. 全链路回归测试。
2. 成本压测（token 上限和降级策略验证）。
3. 修复 P0/P1，冻结范围，准备演示脚本。
交付物：
1. MVP 演示版与发布说明。
验收标准：
1. 核心成功率 > 95%，且成本在预算上限内。

## 5. 里程碑与止损点
1. M1（Day 7）：P0 核心闭环必须完成，否则暂停 UI/登录开发。
2. M2（Day 10）：评估分数和安全链路达标，否则不进入发布准备。
3. M3（Day 15）：发布演示版；若不达标，保留本地演示，暂不上云。

## 6. MVP 后再做（明确延后）
1. 高级推荐排序和复杂画像特征工程。
2. 完整运营后台和策略平台。
3. 大规模 A/B 实验平台。
4. 多模型自动路由和复杂成本优化器。
