# 明日计划 (2026-03-27)

- 计划日期：`2026-03-27`
- 对应阶段：`Day 6 — 双 agent 自动对话 Worker`

## 核心目标
实现 BullMQ Worker 驱动的双 agent 自动对话，完成从会话创建到自动对话完成的闭环。

## 详细任务清单

### 1. BullMQ Worker 基础搭建
- **目标**：将 `apps/worker` 从占位实现升级为可运行的 BullMQ Worker
- **具体任务**：
  - 配置 BullMQ 连接 Redis，实现 Worker 启动/优雅关闭
  - 定义 `conversation` 队列和 job 数据结构
  - 实现 job 重试策略（指数退避，最大 3 次）
  - 添加死信队列（DLQ）处理失败任务
- **预期产出**：Worker 可启动并消费 Redis 队列中的任务

### 2. 对话编排器接入 Worker
- **目标**：将 `conversation-orchestrator.service.ts` 接入 Worker 驱动循环
- **具体任务**：
  - 实现 `ConversationJob` processor：接收 sessionId，驱动 A/B 轮询对话
  - 对话轮次上限控制（默认 10 轮）
  - 单轮超时保护（默认 30s）
  - 整体会话超时保护（默认 5min）
  - 对话结束后自动更新 session 状态为 `completed`
- **预期产出**：创建会话后，Worker 自动驱动双 agent 完成对话

### 3. API 触发入口
- **目标**：在会话创建时自动将对话任务入队
- **具体任务**：
  - 在 `POST /sessions` 路由中，会话创建成功后将 job 推入 `conversation` 队列
  - 添加 `GET /sessions/:id/status` 轮询接口，返回对话进度（当前轮次、状态）
  - 确保幂等：同一 session 不重复入队
- **预期产出**：前端创建会话 → API 入队 → Worker 自动对话 → 前端可轮询进度

### 4. Runtime 集成
- **目标**：Worker 调用 Runtime 生成实际对话内容
- **具体任务**：
  - Worker 内实例化 `AgentRuntimeEngine`，传入当前 persona + 历史消息
  - 解析 Runtime 返回的 `RuntimeTurnResult`，写入消息和记忆
  - 处理 Runtime 失败（fallback 消息 + 标记 session 为 `failed`）
- **预期产出**：对话内容由 LLM 生成（或 fallback），而非硬编码

### 5. 测试与验证
- **目标**：确保 Worker 驱动的对话链路可靠
- **具体任务**：
  - 编写 Worker processor 单元测试（mock Runtime）
  - 编写端到端集成测试：创建会话 → 验证消息写入 → 验证 session 状态变更
  - 运行全量回归：`pnpm test` + `pnpm typecheck`
- **预期产出**：新增测试 5+ 条，全部通过

## 预期成果
1. `apps/worker` 从占位升级为可运行的 BullMQ Worker
2. 创建会话后，Worker 自动驱动双 agent 完成多轮对话
3. 对话有轮次上限和超时保护，异常有 fallback 处理
4. 前端可通过轮询获取对话进度
5. 所有现有测试保持通过

## 风险与依赖
- **风险**：LLM 调用延迟可能导致 Worker 超时，需合理设置 timeout
- **依赖**：Redis 必须可用（BullMQ 底层依赖）；`@agent/runtime` 的 `AgentRuntimeEngine` 已就绪
- **资源**：需要 OpenAI API key 用于 live 模式测试

## 验收标准
1. Worker 可独立启动并消费队列任务
2. 创建会话后 30s 内开始自动对话
3. 对话在达到轮次上限或超时后正确终止
4. Session 状态正确流转：`active` → `completed` / `failed`
5. 消息和记忆正确持久化到数据库
6. 所有测试通过率：100%
7. 类型检查：0 错误
